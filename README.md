# Network Traffic Analysis

[![ci](https://github.com/ashlyn-timothey/network-traffic-analysis/actions/workflows/ci.yml/badge.svg)](https://github.com/ashlyn-timothey/network-traffic-analysis/actions/workflows/ci.yml)
![python](https://img.shields.io/badge/python-3.10%2B-3776AB)
![license](https://img.shields.io/badge/license-MIT-blue)

An MSc portfolio project for local packet-capture triage and investigation.
The Streamlit dashboard accepts authorized PCAP and PCAPNG uploads, summarizes
the traffic supported by the capture, and presents explainable scan and ARP
heuristics. Processing is local; no capture data is sent to a hosted service.

The findings are leads for analyst review, **not proof of malicious activity**.
Validate any conclusion against the packets and a controlled baseline.

## Run locally

Python 3.10 or later is required. From the repository root, create and activate
a virtual environment, then install the application dependency:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m streamlit run app.py --server.address 127.0.0.1
```

Open the local URL printed by Streamlit (normally
`http://127.0.0.1:8501`). The server is configured to bind to localhost and
capture uploads are limited to 50 MB. Select a `.pcap` or `.pcapng` file that
you are authorized to analyze. No sample traffic or fabricated alerts are
generated by the dashboard.

On macOS or Linux, activation is `source .venv/bin/activate`; the other
commands are the same.

The application dependencies include Streamlit and ReportLab. Install the
additional test tools, including the PDF reader used to validate generated
reports, with `python -m pip install -r requirements-dev.txt`.

## Command-line triage

The original CLI remains available and supports text and JSON output:

```powershell
python tools/pcap_summary.py captures/01-port-scan.pcap
python tools/pcap_summary.py captures/02-arp-spoofing.pcap --threshold 20 --json
```

It reports packet and protocol counts, top IPv4 source addresses, UDP/53 DNS
queries, possible vertical/horizontal SYN scans, ICMP echo sweeps, high DNS
query volume, repeated SYN attempts, unusual TCP flag combinations, and ARP
IP-to-MAC conflicts.
The scan threshold is a capture-wide distinct-port/host threshold, not a
time-window rule. Findings include severity, confidence, a reason, first/last
observed times, relevant packet count, bounded packet evidence and investigation
recommendations; evidence is capped at 25 records per finding.

## Detection rules and thresholds

The dashboard exposes the same thresholds as the CLI. They apply to the
uploaded capture as a whole; they are not rates per minute or other normalized
time windows.

| Finding type | Default threshold | Meaning and caveat |
|---|---:|---|
| `vertical_syn_scan` | 15 distinct destination ports | One source sends TCP SYNs to many ports on one IPv4 host. Authorized scanners and monitoring can match. |
| `horizontal_syn_sweep` | 15 distinct IPv4 destinations | One source sends TCP SYNs to multiple IPv4 hosts. Discovery and inventory tools can match. |
| `possible_icmp_sweep` | 10 distinct IPv4 destinations | One source sends ICMP echo requests to multiple IPv4 hosts. Health checks and monitoring can match. |
| `high_dns_query_volume` | 100 extractable UDP/53 queries from one source | Counts DNS query messages whose first uncompressed question name can be extracted. Long captures, busy clients, retries, and recursive resolvers can match; this is not a DNS-tunneling detector. |
| `repeated_connection_attempts` | 20 TCP SYN packets to one destination/port from one source | Retries, retransmissions, duplicated captures, or an unavailable service can match; packets are not session-reassembled. |
| `arp_ip_claimed_by_multiple_macs` | 2 distinct sender MACs for an IP | An observed claim conflict can also reflect failover, reassignment, or virtualization. |
| `unusual_tcp_flag_combination` | One SYN with FIN or RST also set | A header-level anomaly only; diagnostic tools, malformed packets, and middleboxes can produce it. |

Change thresholds in the dashboard's **Detection thresholds** sidebar, or use
the CLI flags:

```powershell
python tools/pcap_summary.py capture.pcapng --threshold 20 `
  --icmp-sweep-threshold 12 --dns-volume-threshold 200 `
  --repeated-syn-threshold 30 --json
```

All findings are descriptive triage hypotheses, not verdicts. Severity and
confidence communicate review priority and evidence strength, not a calibrated
probability of compromise. Validate rules against controlled positive and
negative captures and the local environment before operational use.
DNS question extraction is limited to complete, uncompressed names that meet
the wire-format limits (63 bytes per label and 255 encoded bytes per name);
malformed or incomplete question records are ignored.

## Tests

Install the test dependency and run the complete suite:

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

The original nine `unittest` cases remain available:

```powershell
python -m unittest discover -s tests -v
```

The tests use synthetic PCAP and PCAPNG data; they do not scan networks or rely
on real captures.

## Architecture

```text
app.py                         Streamlit dashboard
network_traffic_analysis/
  capture.py                   PCAP/PCAPNG readers and format validation
  models.py                    packet and finding data models
  analysis.py                  packet decoding and capture summaries
  detections.py                explainable heuristic rules
  investigations.py            local SQLite persistence and timeline
  reporting.py                 in-memory SOC investigation PDF generation
data/
  investigations.sqlite3       created locally on first dashboard launch
tools/pcap_summary.py          backwards-compatible CLI
tests/                         synthetic capture tests
cases/                         investigation write-ups
docs/                          lab setup and Wireshark reference
captures/                      optional, authorized sample captures
```

The dashboard stores saved investigations in `data/investigations.sqlite3` on
the local machine. Captures are analyzed in memory and are **not** saved. The
database contains investigation metadata, analysis summary JSON, findings, and
bounded structured packet evidence; packet payload bytes are not retained.
Upload-received, investigation-created, and last-updated times are stored
separately from capture packet timestamps.

The database schema version is stored in SQLite's `PRAGMA user_version`
(currently version 2). On startup the application applies supported schema
migrations in a transaction and only advances the version after the migration
succeeds. The migration preserves legacy investigations, initializes their
last-updated time from their creation time where needed, adds
duplicate-submission metadata, and creates analyst-assessment, evidence-review,
and append-only activity-history storage. A database with a newer or
incompatible schema is reported as unavailable; it is not reset or overwritten.

### Investigation workspace

Use the dashboard sections to:

1. Analyze a capture in **New Analysis** and enter an investigation name.
2. Select **Save investigation** to store the summary and findings locally.
3. Browse **Investigations**, then open an item in **Investigation Details**.
4. Change status (Open, In Progress, Resolved), save an analyst conclusion and
   notes, and review each finding as Needs Review, True Positive, False
   Positive, or Inconclusive. Analyst reasoning and review time are stored
   separately from the original automated detection. Analyst notes are limited
   to 20,000 characters; longer existing notes remain intact and can be shortened
   before saving further changes.
5. Mark individual bounded packet evidence Reviewed or Not Reviewed. Review
   status does not alter the stored packet metadata. Investigation changes are
   recorded in chronological activity history.
6. To delete, open its details, check the explicit permanent-deletion
   confirmation, then select **Delete investigation**. Findings are deleted
   with their parent investigation; related evidence-review and activity
   records are removed with it.

Back up the database by stopping the dashboard and copying
`data/investigations.sqlite3` to a protected local backup location. Keep backups
private because they may contain analyst notes and network indicators. Restore
by stopping the app and restoring the database file to that path. Keep a
separate untouched copy before upgrading the app; do not remove SQLite
`-wal`, `-shm`, or journal files while the application is running. The app does
not delete or replace database files or sidecars during startup.

The database path is local and is ignored by Git. There is no account system or
database encryption; protect the host and backups accordingly. The timeline
contains only packet evidence retained by detections (at most 25 evidence
packets per finding), not every packet in the capture. Capture timestamps are
shown in UTC; upload-received and investigation-created timestamps are app-side
UTC times, not packet events. The MVP does not yet support editing an
investigation name, attaching new captures to a saved investigation, or
manual schema rollback. Re-saving a capture under the same investigation name
is blocked when its SHA-256 digest matches an existing saved capture; use a
different name to intentionally create a separate investigation. Historical
records created before digest tracking cannot be matched this way.

### PDF investigation report export

Open a saved investigation in **Investigation Details**, select **Generate PDF
Report**, then use **Download PDF report**. The report is generated in memory
for the currently selected investigation and downloaded as
`investigation_report_<investigation-id>.pdf`.

The report includes investigation metadata, generation time, packet and
protocol summaries, severity counts, finding explanations and recommendations,
bounded structured packet evidence with review status, an evidence-derived
timeline, saved analyst notes and conclusion, each finding's disposition and
analyst reasoning, and recent investigation activity history. Automated
detections and analyst assessments are clearly separated. Capture event times
are shown separately from application-created and updated times. Missing values
are marked as unavailable rather than inferred.

ReportLab is installed locally through `requirements.txt`; `requirements-dev.txt`
includes `pypdf` for validating PDF output in tests. Report generation uses
persisted investigation data only, excludes arbitrary payload fields, escapes
untrusted text, omits local capture paths, and does not write reports into the
repository or send data to external services. Reports can still contain
sensitive investigation names, IP addresses, evidence metadata, and analyst
notes; store downloaded reports accordingly. Text glyphs unavailable in the
bundled report font are displayed as `[U+XXXX]` code points instead of being
silently lost.

Reports are limited to data saved by the analyzer. Evidence lists are capped at
25 packets per finding; omitted evidence is identified as such. Protocol
visibility and detection quality remain limited by the capture parser and
heuristic rules described above. The PDF is a formatted record for review, not
a validated incident verdict or a replacement for the source capture.

To select another local database file, set `NTA_DATABASE_PATH` before starting
Streamlit, for example in PowerShell:

```powershell
$env:NTA_DATABASE_PATH = "D:\private\nta-investigations.sqlite3"
python -m streamlit run app.py --server.address 127.0.0.1
```

## Scope and limitations

- Ethernet, IPv4, TCP, UDP, ICMP, ARP, one or more VLAN tags, and unencrypted
  DNS queries over UDP/53 are summarized. Other link types are skipped.
- IPv6, TCP DNS, encrypted DNS, protocol reassembly, and user accounts are not
  implemented.
- Capture parsing is bounded by the 50 MB dashboard upload limit but the
  command-line tool reads the input file into memory.
- SYN scan thresholds are capture-wide and can alert on benign scanning or
  monitoring. ARP conflicts can occur during legitimate network changes.
- No detector has been validated against a representative corpus of controlled
  positive and negative captures; treat every result as a triage hypothesis.

## Safety

Use captures you created or are authorized to analyze. Keep experiments in an
isolated lab and remove credentials, tokens, personal data, and third-party
traffic before sharing a capture. No offensive functionality is provided.
